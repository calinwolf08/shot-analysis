# Pro reference data → accurate targets (and per-pro profiles)

**Goal:** turn pro shot videos — filmed at whatever angle they were filmed,
mostly _not_ a true side view — into metric values that match what the app
measures for a user filmed side-on, then build the app's targets from many
pros (not just Curry), and keep a per-pro profile for later analysis
("which pro are you closest to").

Every step is reviewed by a person in the validator tool
(`validate-metrics.html`): which attempts are used, the key frames, the camera
angle and any metric that looks wrong. The target build only uses what was
approved there.

## Background: what we found

- **Curry's clip is ~35–40° off side-on.** Measured from apparent shoulder and
  hip width vs torso length; shoulders and hips agree. MediaPipe's depth guess
  says ~20° but is known to under-read. The test shot is ~3–10° off.
- **The 1/cos stretch** (horizontal distances ÷ cos(angle)) is what the angle
  costs a side-on metric. Correcting it changed some Curry bands (knee bend at
  load 126–140° → 115–130°, set-point knee 139–172° → 148–171°, set-point
  elbow 37–75° → 45–66°). The test shot's total didn't change.
- **The biggest error at an angle comes from mixing body sides.** Torso lean
  uses the near hip → near shoulder; shoulders are wider than hips, so at 40°
  the near line tilts ~12° compared to the far one. That is the source of
  Curry's odd −7° to −15° "backward lean" target. Measured on the centre line
  (mid-shoulders → mid-hips), Curry's load lean is about −3° (upright).
- **Even an exact angle doesn't correct everything.** What remains:
  - sideways movement leaks in at tan(angle) (elbow flare, knees out, guide
    hand, shoulders/hips turning);
  - perspective and camera tilt (not correctable without the camera's full
    pose; the clips show no full court);
  - MediaPipe's own errors, which grow at oblique angles.
    At 10–15° off all of this is below tracking noise; it matters from ~20–25°.
- **The camera angle has to come from the body.** No full court is in view.
  Use apparent shoulder/hip width over the shot (dip → set point), calibrated per shooter from their
  widest frames. Scenery (backboard corners, two parallel floor lines, floor
  boards) is an optional cross-check. Expect ±5°, which is ~0.5–1° on joint
  angles at 20° off. A data-driven step (Phase 4) removes any consistent bias.
- **Users need no correction.** The app only checks that the phone is within
  ~20° of side-on and warns otherwise.

## Data layout (committed, under `reference-data/`)

```
reference-data/
  players/

      player.json        # name, shootingHand, proportions (generated), notes
      <clip>/
```

```jsonc
        "source": "auto" | "manual" | "scenery",
```

Existing `labels.json` (v1, key frames at the shot's top level) is read as
v2 with `status: "unreviewed"` and no camera block. The validator writes v2.

## Phase 1 — Measurement fixes (shared metric code)

These changes go in `src/metrics/v3`, so the app, the validator and the target
build measure identically.

1. **Centre-line torso.** Torso lean, its changes and the rise/release spine
   metrics use mid-shoulders → mid-hips. Review every metric that pairs points
   from opposite sides; use same-side points or centre lines where the metric
   allows. Head pitch keeps ear → nose.
2. **Camera-angle estimate** (`camera-angle.ts`, pure):
   - per frame: shoulder width ÷ torso length and hip width ÷ torso length;
   - angle = asin(ratio ÷ frontal ratio), with the frontal ratio taken from the
     shooter's proportions when known, else population defaults
     (shoulders 0.80, hips 0.50);
   - per attempt: the median over the dip → set point (frames before the dip
     are unreliable: players are often still turning into the shot);
   - returns shoulders, hips, combined, and the frames used;
   - flags shoulder/hip disagreement over 8° (standing open / rotating).
3. **Proportions** (`proportions.ts`): from a player's clips, the median
   segment lengths (thigh, shin, torso, upper arm, forearm) as ratios of torso
   length, from near-side-on frames. Frontal shoulder/hip widths come from the
   widest frames (near the 95th percentile, to skip glitches).
4. **Measuring from given events:** `computeShotMetricsV3(frames, opts,
events?)`. When labelled key frames are passed, they replace the detected
   events (labels map to events through `LABEL_FOR_EVENT`; extend it with
   release and the foot events where metrics use them).
5. **Angle correction option:** `opts.cameraAngle`. Horizontal coordinates are
   stretched by 1/cos(angle) about the body centre before signals are computed.
   It's off for users.
6. **Re-baseline:** rebuild the Curry targets and goldens, and update tests.
   Expect the torso lean bands to move toward upright.

**Tests:**

- Synthetic poses rotated by known angles: the estimate recovers the angle
  (±2° with exact proportions), and correction restores in-plane metrics.
- Centre-line lean is unaffected by shoulder/hip width at an angle.
- Labelled events override detection.

## Phase 2 — Validator: review everything per attempt

Build on `validate-metrics.html` + `server.ts`, which already handle pose
extraction, key-frame labelling and labelled-vs-detected comparison.

1. **Library view:**
   - a tree of players → clips → attempts, with the status per attempt and
     counts per player (approved / excluded / flagged / unreviewed);
   - filters, e.g. "flagged" or "angle > 20°";
   - create a player (name, shooting hand) and add a clip (video → pose
     extraction → `poses.json`).
2. **Key frames:**
   - label them as today;
   - next to each label, the frame the app detects, and the difference
     colour-coded (within tolerance / off / missing);
   - click either to seek.
3. **Camera angle:**
   - the automatic estimate, its shoulder and hip parts, and the frames used
     (highlighted on the timeline);
   - an adjustment slider, a "confirm" button and a "standing open" checkbox;
   - optional scenery check: click 4 backboard corners, or 2 points on each of
     2 parallel floor lines → angle (stored with `source: "scenery"`).
4. **Metrics, as in the app:**
   - the v3 scorecard, using the same wording file, 0–10+ scale and phase
     order, against the current targets;
   - clicking a metric shows the pose at its frame with the highlighted body
     part and target zone (same drawing code as the app's shot review);
   - per metric: the raw value, the angle-corrected value, and the value from
     labels vs from detection;
   - "outside this player's other shots" badge (more than 2 robust spreads
     from the player's median);
   - a flag button with a note (→ `metricFlags`).
5. **Decision:** approve / exclude (with a reason) / flag for later; saved to
   `labels.json` v2. Keyboard shortcuts for moving through attempts quickly.
6. **Automatic flags (shown, never applied silently):**
   - the angle is over a metric's limit (Phase 3 table);
   - shoulder and hip estimates disagree;
   - a detected key frame is far from the label;
   - a value is an outlier for the player;
   - tracking confidence is low.
7. **Server:**
   - `GET /api/library` (tree + statuses);
   - `GET/POST` clip `labels.json` v2 and `player.json`;
   - existing save routes pointed at `reference-data/players/<player>/<clip>/`.

The validator loads the shared metric code from the browser bundle
(`npm run build:browser`) and the targets/wording from the app's
`static/` folder, so it shows exactly what the app would.

**Tests:**

- Unit tests for the v1 → v2 labels upgrade and the library tree.
- A Playwright smoke test of the validator: load a clip, change the angle,
  flag a metric, approve the attempt, check the saved `labels.json`.

## Phase 3 — Target build from approved data

A new script `npm run targets:build:pros` (`src/testing/build-pro-targets.ts`)
replaces `targets:build:v3` as the source of the app's targets.

1. **Input:** every `approved` attempt (with `flagged` attempts optional via a
   CLI switch).
2. **Per attempt:**
   - metrics from the **labelled key frames**, with the confirmed camera angle
     applied;
   - drop metrics that are flagged, or that exceed their angle limit:

     | Metrics                                                                                            | Max angle off side-on |
     | -------------------------------------------------------------------------------------------------- | --------------------- |
     | Knee and hip angles, centre-line torso lean, hips/knees over ankles, set-point and release heights | 25°                   |
     | Timing metrics                                                                                     | 25°                   |
     | Elbow, wrist, elbow path, head pitch, ball close                                                   | 15°                   |
     | Guide hand                                                                                         | never from side clips |

     These limits live in a config file and are re-tuned by Phase 4.

3. **Per player:**
   - each metric's value = the weighted mean of their attempts, weight
     cos²(angle), so near-side-on shots count more;
   - their spread = the robust standard deviation (from the MAD);
   - also the number of shots and the range of angles covered;
   - their proportions go into `player.json`.
4. **Pooled targets:**
   - every player counts equally;
   - band = the 20th–80th percentile of pooled pro shots (shots weighted so
     each player sums to 1); the percentiles are set per metric in config;
   - ideal = the median;
   - score step (`rampSd`) = the pooled robust spread;
   - metrics where pros disagree far more than any one pro varies
     (between-player spread over ~2× within-player) are reported as **style**,
     and by default become unscored details.
   - Output: `app/static/reference/live-targets-v3.json`, same format; hand
     edits (wording/override) are kept as today.
5. **Per-pro profiles:** `app/static/reference/pro-profiles.json`:

   ```jsonc
   {
     "version": 1,
     "builtAt": "…",
     "metricsSchema": 3,
     "pros": [
       {
         "id": "curry",
         "name": "Stephen Curry",
         "shootingHand": "right",
         "shots": 21,
         "angles": [4, 28],
         "metrics": {
           "load.knee_depth": { "value": 122.4, "spread": 3.1, "n": 21 },
         },
       },
     ],
   }
   ```

6. **Report** (`reference-data/out/report.md`):
   - per metric: the share of pro shots scoring 0 and the average pro score;
   - the style list;
   - detection-vs-label accuracy (median and 90th-percentile frame error per
     event, per player);
   - attempts dropped and why.
     Detection errors above tolerance are fixed in detection before the targets
     are trusted, because users are measured with detection.

**Tests:**

- Fixture library with 2 synthetic players: exclusions, angle limits, flags,
  equal player weighting and percentile bands behave as specified.
- Re-running on unchanged data gives identical output.

## Phase 4 — Remove leftover angle error (data-driven)

Once there are roughly 6–10 pros with angles spread between ~0° and 25°:

1. **Fit the slope** for each metric: value vs confirmed angle, across all
   approved attempts, with a per-player offset (a mixed / within-player fit).
2. **If the slope is significant,** correct each attempt to its 0° value
   (value − slope × angle) before aggregating. Store the slopes in the config
   and print them in the report.
3. **Tune the angle limits:** a metric whose residual spread grows quickly
   with angle gets a lower limit.
4. **Sanity check:** timing metrics should show ~no slope; a large slope there
   points to a bug.
5. **The validator shows** the 0°-corrected value as well.

This also absorbs consistent bias in the body-width angle estimate, so the
proportion defaults don't have to be exact.

## Phase 5 — Pro profiles in the app

1. Load `pro-profiles.json` beside the targets (same loader and caching).
2. **"Closest pro"** (Insights):
   - the user's recent per-metric averages (from stored shot metrics) against
     each pro;
   - distance = the mean of |user − pro| ÷ the pro's spread over scored,
     measured metrics, with style metrics included here, since style is the
     point;
   - show the closest 3 and the metrics that match best and worst.
3. **"Score against a pro"** (a setting): score shots against one pro's values
   instead of the pooled targets.
   - band = pro value ± their spread, widened to at least the pooled band's
     minimum width;
   - default stays pooled.
4. **User camera check:** warn in the live setup when the phone is more than
   ~20° off side-on (same estimate, population proportions).

panel needs Phase 1.

## Data to collect

- **10+ shooters,** several clips each, at angles spread between ~0° and 25°
  off side-on. A spread of angles is what lets Phase 4 measure leftover error;
  different shots per angle are fine.
- **Mostly side-on clips for the arm metrics** (elbow, wrist, elbow path).
- **Frames where the player turns toward the camera** help the per-shooter
  proportions (walking back, between shots).
- **Later, face-on clips** for the guide-hand and side-to-side metrics: a
  separate view with its own metrics, outside this plan.
